# 2.1 Nomor HP di POS

| Fase | Prioritas | Estimasi | Prasyarat | Keputusan |
|---|---|---|---|---|
| 2 — Bukti ke customer | P1 | S | — | — |

## Tujuan

Walk-in yang mau dikirimi struk/promo bisa dihubungi. POS hari ini hanya mencatat **nama** (`customer_name`), padahal nomor HP adalah data CRM yang paling berguna — Komunikasi dan Tagih via WA (2.4) memakainya. Sekaligus membuat pencocokan customer lebih aman: HP lebih unik daripada nama.

## Lingkup

**Termasuk**
- Input HP opsional di POS, disimpan ke `customers.phone`.
- Helper normalisasi nomor `Phone::normalise()` (baru) — dipakai juga 2.4, 3.4.
- Pencocokan customer: HP dulu, lalu nama.

**Tidak termasuk**
- Pencarian/pemilihan customer dari daftar di POS (`ponytail` di `PosController::customerFor` tetap berlaku; dibahas di 3.4 untuk form order).
- Normalisasi HP di `CustomerRequest` (menu Customer) — bisa ikut kalau murah, tapi bukan syarat; kalau dilakukan, satu baris `Phone::normalise()` di `CustomerController::store/update`.
- Validasi format HP ketat (panjang digit) — nomor luar negeri ada; cukup `max:30`.

## Aturan bisnis

1. `customer_phone` hanya berarti bila `customer_name` terisi. Nama kosong + HP terisi → **walk-in tanpa customer** (HP diabaikan). Alasan: baris customer tanpa nama tidak berguna di daftar blast dan menghitung jumlah customer palsu (lihat komentar `orders.customer_id` di migrasi).
2. HP dinormalkan sebelum disimpan/dicocokkan: hanya digit; awalan `0` → `62`; awalan `+62` → `62`; sudah `62` dibiarkan. Sama dengan `keNomorWa()` di `resources/js/lib/format.ts` supaya tautan `wa.me` di seluruh app konsisten.
3. Urutan pencocokan: (a) customer dengan `phone` sama (setelah normalisasi) → pakai; (b) tidak ada → customer dengan nama sama case-insensitive (perilaku sekarang) → pakai; (c) tidak ada → buat baru dengan nama + HP.
4. Kasus (b) dan customer itu belum punya HP → **isi** `phone`-nya dengan yang baru diketik (melengkapi). Kalau sudah punya HP berbeda → **jangan timpa**; pakai customer itu apa adanya (owner memperbaiki di menu Customer). Alasan: menimpa diam-diam menghilangkan data; dua orang bernama sama dengan HP berbeda lebih mungkin daripada satu orang ganti nomor.
5. Nomor HP yang disimpan adalah bentuk ternormalisasi (`628…`), bukan ketikan mentah. `customers.phone` lama yang masih `08…` dibiarkan — `keNomorWa()` di klien tetap menanganinya; pencocokan (a) membandingkan hasil normalisasi kedua sisi (lihat Backend).

## Perubahan data

Tidak ada migrasi: `customers.phone` (`string nullable`) sudah ada.

**Baru:** `Modules\Customer\Support\Phone` (direktori `Support/` baru di modul Customer — Shared sudah punya pola `Modules/Shared/Support/Money.php`).

```php
final class Phone
{
    /** "0812-3456" → "628123456"; "+62 812" → "62812"; "62812" tetap. Kosong → "". */
    public static function normalise(string $raw): string
    {
        $digits = preg_replace('/\D+/', '', $raw) ?? '';
        if ($digits === '' || str_starts_with($digits, '62')) {
            return $digits;
        }

        return preg_replace('/^0/', '62', $digits) ?? $digits;
    }
}
```

Catatan desain: ditaruh di modul **Customer** (pemilik data HP), bukan Shared — Order memanggil lintas modul sesuai batas pragmatis (`docs/development.md`). Tidak dibuat cast/mutator Eloquent di `Customer::phone` supaya data lama `08…` tidak ikut berubah bentuk saat dibaca-tulis tanpa sengaja.
