# 4.4 Split payment di POS

| Fase | Prioritas | Estimasi | Prasyarat | Keputusan |
|---|---|---|---|---|
| 4 — Kenyamanan transaksi | P3 | M | 2.2 (flash `receipt`) | — |

## Tujuan

Customer membayar sebagian tunai, sebagian QRIS — dua baris pembayaran tercatat sesuai metodenya, sehingga Kas Harian per metode (3.3) dan pencocokan laci/rekening tetap benar.

## Lingkup

**Termasuk**
- POS menerima 1–2 pembayaran dengan metode berbeda yang jumlahnya = total.
- Field lama `method` **dihapus** dari request — satu jalur saja.
- Struk (2.2) menampilkan tiap baris pembayaran.

**Tidak termasuk**
- Split di *Catat Bayar* order studio/event — di sana sudah bisa dicatat dua kali berturut-turut (pembayaran banyak-ke-satu); tidak perlu UI khusus.
- Lebih dari 2 metode — tiga metode yang ada (`cash`, `transfer`, `qris`); dua sudah menutup kasus nyata. Batas di validasi `max:2`.
- Kembalian (uang tunai diterima > total) — POS mencatat yang **menjadi omzet**; kembalian urusan laci. Kalau ingin kalkulator kembalian, itu UI klien saja, bukan data.

## Aturan bisnis

1. `payments` array, minimal 1, maksimal 2; tiap baris `method` (enum) dan `amount` integer ≥ 1.
2. `Σ amount` harus **sama persis** dengan `subtotal − discount`; selisih → 422 di `payments` "Jumlah pembayaran Rp X tidak sama dengan total Rp Y".
3. Dua baris tidak boleh bermetode sama (gabungkan saja) → 422 di `payments.1.method`.
4. Setiap baris jadi satu baris `payments` dengan `paid_on = today`, `note = 'Pelunasan'` (dua baris → `'Pelunasan (1/2)'`, `'Pelunasan (2/2)'` supaya di invoice terbaca sebagai satu transaksi).
5. Order tetap `delivered` + lunas dalam satu transaksi DB — sama seperti sekarang.
6. Satu baris (kasus normal) harus tetap **satu klik**: UI default satu metode dengan amount otomatis = total; baris kedua hanya muncul lewat "+ Bagi pembayaran".

## Perubahan data

Tidak ada — skema `payments` sudah banyak-ke-satu.

## Backend

### Route
Tidak ada (tetap `pos.store`).

### Request
`StorePosSaleRequest`:
- Hapus `'method' => ['required', Rule::enum(PaymentMethod::class)]` dan atributnya.
- Tambah:
  ```php
  'payments' => ['required', 'array', 'min:1', 'max:2'],
  'payments.*.method' => ['required', Rule::enum(PaymentMethod::class)],
  'payments.*.amount' => ['required', 'integer', 'min:1'],
  ```
- `after()`: setelah cek diskon yang ada, bila tanpa error: `array_sum(amount) !== subtotal − discount` → error `payments`; dua baris metode sama → error `payments.1.method`.
- Helper `payments(): list<array{method: PaymentMethod, amount: int}>`.
- `attributes()`: `payments` → "pembayaran", `payments.*.method` → "metode bayar", `payments.*.amount` → "jumlah bayar".

### Controller / Action / Service
`PosController@store`: ganti satu `payments()->create([...])` dengan loop atas `$request->payments()`; `note` sesuai aturan 4. Flash `receipt` (2.2) sudah memuat `invoice_url` — struk membaca pembayaran dari invoice publik, tidak perlu field tambahan.

### Props Inertia
Tidak ada perubahan di `pos.index`. Invoice/struk sudah mengirim `payments[]`.

## Frontend

- `pos.tsx`: `SaleForm.method` → `SaleForm.payments: { method: PaymentMethod; amount: string }[]` (default `[{ method: 'cash', amount: '' }]`). Saat satu baris, `amount` **tidak ditampilkan** dan dikirim = `total` (dihitung saat submit, bukan disimpan di state — supaya ikut berubah bila keranjang berubah).
- Tombol teks "+ Bagi pembayaran" di bawah pemilih metode → baris kedua: `ToggleGroup` metode (opsi yang sudah dipakai baris pertama nonaktif) + input nominal. Nominal baris pertama jadi `total − amount2` otomatis (hanya baris kedua yang diketik — mencegah dua angka yang harus dicocokkan manual). Tombol ikon hapus mengembalikan ke satu baris.
- Validasi klien: `amount2` harus 1..total−1; tombol simpan nonaktif bila tidak.
- Error server `errors.payments`, `errors['payments.1.method']` via `InputError`.
- Komponen struk (2.2) sudah memetakan `payments[]` — verifikasi tampil dua baris; tidak ada perubahan selain pastikan `note` "Pelunasan (1/2)" terbaca wajar.
