# 0.2 Riwayat perubahan order (`order_events`)

| Fase | Prioritas | Estimasi | Prasyarat | Keputusan |
|---|---|---|---|---|
| 0 — Fondasi jejak | P1 | M | — (0.1 disarankan lebih dulu agar `user_id` dan `created_by` konsisten) | — |

## Tujuan

Menjawab "siapa yang mengubah jadwal ini, kapan, dari apa ke apa" dan "kapan status diturunkan". Hari ini order hanya punya `updated_at`; begitu order boleh diedit (1.2) dan status boleh mundur (1.4), tanpa riwayat prinsip "riwayat tidak diedit" (`docs/database.md`) hilang diam-diam. Dipakai oleh 1.2, 1.4, 4.2.

## Lingkup

**Termasuk**
- Tabel `order_events` (baru) + model + satu action pencatat `RecordOrderEvent` (baru).
- Pemasangan di **semua** jalur tulis order yang sudah ada: buat (form & POS), lanjut status, batal, link hasil, catat/hapus pembayaran.
- Bagian "Riwayat" di Sheet detail order.

**Tidak termasuk**
- Event untuk biaya job (`JobCost`) — dicatat di modul Expense, bukan perubahan order; `created_by` (0.1) sudah cukup.
- Riwayat untuk katalog/customer/aset — tabel ini khusus order; tabel generik "audit log" ditunda sampai ada kebutuhan kedua.
- Tipe `updated`, `reverted`, `refunded` **didefinisikan** di sini tapi baru **dipancarkan** oleh 1.2, 1.4, 4.2.
- Backfill untuk order lama — riwayat dimulai sejak fitur ini aktif; UI menampilkan "Riwayat tersedia sejak {tanggal deploy}" bila kosong untuk order yang `created_at`-nya lebih tua dari event pertama di tabel.

## Aturan bisnis

1. Setiap event memiliki `type` dari daftar tetap: `created`, `updated`, `advanced`, `reverted`, `cancelled`, `payment_recorded`, `payment_deleted`, `result_link`, `refunded`. Tipe di luar daftar ditolak di level kode (enum), bukan DB.
2. Event dicatat **di dalam transaksi yang sama** dengan perubahan yang dicatatnya — tidak ada perubahan tanpa event, tidak ada event tanpa perubahan.
3. Event tidak pernah diubah atau dihapus oleh app (hanya `created_at`, tanpa `updated_at`, tanpa route destroy). Menghapus order (tidak ada di app) akan menghapus eventnya (`cascadeOnDelete`) — konsisten dengan `order_items`.
4. `user_id` = user login saat itu; `null` kalau tanpa sesi (seeder) atau user sudah dihapus. Event tetap ada.
5. `changes` menyimpan **hanya field yang berubah**, bentuk `{field: {from, to}}`; nilai disimpan apa adanya (tanggal `Y-m-d`, jam `H:i`, enum `value`, uang integer). Event tanpa perubahan field (`created`, `payment_*`) menyimpan ringkasan di `changes` juga (lihat tabel di bawah) supaya UI tidak perlu join ke tabel lain.
6. Urutan tampil = `created_at` desc, lalu `id` desc (dua event dalam satu detik tetap stabil).

## Perubahan data

Migrasi `2026_10_xx_000002_create_order_events_table.php`:

```php
Schema::create('order_events', function (Blueprint $table) {
    $table->id();
    $table->foreignId('order_id')->constrained()->cascadeOnDelete();
    // Null = tanpa sesi (seeder) atau user sudah dihapus — event tetap ada.
    $table->foreignId('user_id')->nullable()->constrained()->nullOnDelete();
    $table->string('type'); // OrderEventType
    // Hanya field yang berubah: {field: {from, to}}. Null untuk tipe tanpa rincian.
    $table->jsonb('changes')->nullable();
    // Tanpa updated_at: event tidak pernah diubah.
    $table->timestamp('created_at');

    $table->index(['order_id', 'created_at']);
});
```

`jsonb` (bukan `json`) karena PostgreSQL — konsisten kalau nanti perlu query `changes->>'work_status'`. `down()` → `dropIfExists('order_events')`.

Model `Modules\Order\Models\OrderEvent` (baru): `#[Fillable(['order_id','user_id','type','changes'])]`, `public $timestamps = false` + `const CREATED_AT = 'created_at'` dan set `created_at` di `creating` (atau `$table->timestamp('created_at')->useCurrent()` — pilih `useCurrent()`, lebih sedikit kode), cast `type` → `OrderEventType`, `changes` → `array`. Relasi `order()`, `user(): BelongsTo<User>`. Docblock `@property` lengkap (PHPStan level 7).

Enum `Modules\Order\Enums\OrderEventType: string` (baru) dengan 9 case di atas + `label(): string`:

| Case | Label | Isi `changes` |
|---|---|---|
| `created` | Dibuat | `{work_status: {from: null, to}, total: {from: null, to}}` |
| `updated` | Diubah | field yang berubah (1.2) |
| `advanced` | Status maju | `{work_status: {from, to}}` |
| `reverted` | Status dikembalikan | `{work_status: {from, to}}` (1.4) |
| `cancelled` | Dibatalkan | `{work_status: {from, to: 'cancelled'}, reason: {from: null, to}}` |
| `payment_recorded` | Pembayaran dicatat | `{amount: {from: null, to}, method: {from: null, to}, paid_on: {from: null, to}}` |
| `payment_deleted` | Pembayaran dihapus | `{amount: {from, to: null}, method: {from, to: null}, paid_on: {from, to: null}}` |
| `result_link` | Link hasil | `{result_link: {from, to}}` |
| `refunded` | Pengembalian | `{amount, method, reason}` (4.2) |

`Order` menambah relasi `events(): HasMany<OrderEvent>`.

### Controller / Action / Service

`Modules\Order\Actions\RecordOrderEvent` (baru) — satu pintu, pola sama `Finance\Actions\RecordInvestment`:

```php
final class RecordOrderEvent
{
    /** @param array<string, array{from: mixed, to: mixed}> $changes */
    public function execute(Order $order, string $type, array $changes = []): OrderEvent
    {
        return $order->events()->create([
            'user_id' => auth()->id(),
            'type' => OrderEventType::from($type),
            'changes' => $changes === [] ? null : $changes,
        ]);
    }
}
```

Dipanggil (di dalam `DB::transaction` yang sudah ada, atau dibungkus transaksi baru bila belum ada — `advance`, `cancel`, `updateResultLink`, dan `OrderPaymentController` hari ini **tidak** bertransaksi; bungkus `DB::transaction` di sana):

| Titik | File | Tipe |
|---|---|---|
| `OrderController@store` | `Modules/Order/Controllers/OrderController.php` | `created`, lalu `payment_recorded` bila DP > 0 |
| `PosController@store` | `Modules/Order/Controllers/PosController.php` | `created`, `payment_recorded` |
| `OrderController@advance` | | `advanced` |
| `OrderController@cancel` | | `cancelled` |
| `OrderController@updateResultLink` | | `result_link` |
| `OrderPaymentController@store` | `Modules/Order/Controllers/OrderPaymentController.php` | `payment_recorded` |
| `OrderPaymentController@destroy` | | `payment_deleted` (setelah `OpenPeriod::ensureOpen`, sebelum `delete()`) |

Injeksi action lewat parameter method (`RecordOrderEvent $events`) — konsisten dengan `ReceivableController@index(Receivables $receivables)`.

Eager-load: `OrderController@index/calendar` → `with([... 'events.user'])`. Kalender tidak menampilkan riwayat, tapi memakai `orderProps()` yang sama — terima biaya kecil ini daripada dua bentuk props.

### Props Inertia

`orderProps()` menambah:

```ts
events: {
    id: number;
    type: OrderEventType;              // 9 literal di types.ts
    changes: Record<string, { from: unknown; to: unknown }> | null;
    user_name: string | null;          // null = sistem/seeder/user dihapus
    at: string;                        // ISO 8601, created_at
}[];
```

Urut terbaru dulu (`sortByDesc('created_at')->sortByDesc('id')` di PHP, atau `orderByDesc` di relasi: `events()->orderByDesc('created_at')->orderByDesc('id')`).
