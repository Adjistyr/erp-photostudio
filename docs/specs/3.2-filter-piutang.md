# 3.2 Filter piutang (klien)

| Fase | Prioritas | Estimasi | Prasyarat | Keputusan |
|---|---|---|---|---|
| 3 — Skala & jalan pintas harian | P2 | S | 3.1 (`list-toolbar.tsx` mode klien) | — |

## Tujuan

Layar Pembayaran (`order::receivables`) menampilkan semua piutang urut sisa terbesar. Owner yang mau menagih **yang sudah lewat jatuh tempo saja**, atau mencari satu customer, harus memindai seluruh tabel. Daftar ini kecil (puluhan baris, semua dimuat `Receivables::open()`) → filter di klien cukup; tidak perlu request.

## Lingkup

**Termasuk**
- Tab umur: **Semua / Lewat jatuh tempo / ≤ 7 hari lagi**.
- `Select` lini dan input cari (nomor order / nama customer) lewat `ListToolbar` mode klien.
- Fungsi filter murni di `modules/order/lib/receivables-filter.ts` (baru) supaya bisa di-Vitest.

**Tidak termasuk**
- Paginasi / query server — `Receivables::open()` tetap memuat semua (komentar ponytail di service itu sudah menyebut ambangnya: ribuan order aktif).
- Pengurutan ulang kolom.
- Tombol Tagih via WA — 2.4.
- Mengubah kartu ringkasan — kartu tetap untuk **seluruh** piutang (aturan 3).

## Aturan bisnis

1. Tab **Lewat jatuh tempo** = `days_until_due < 0` — sama persis dengan kartu "Lewat jatuh tempo" dan `Receivables::overdue()` (jatuh tempo hari ini dihitung *belum* lewat).
2. Tab **≤ 7 hari lagi** = `0 <= days_until_due <= 7`.
3. Kartu ringkasan (total, lewat jatuh tempo, belum jatuh tempo) dan peringatan konsentrasi > 50 % **tidak** ikut filter — angka risiko harus utuh. Caption di bawah kartu menyatakannya saat filter aktif: "Kartu menghitung seluruh piutang; tabel di bawah difilter."
4. Pencarian cocok tanpa membedakan huruf besar pada `number` dan `customer_name`; "Walk-in" (customer null) cocok dengan ketikan "walk".
5. Filter adalah state komponen (bukan URL) — layar ini selalu dibuka untuk hari ini dan tidak dibagikan; konsisten dengan `ReportNav` yang menyebut "Piutang selalu per hari ini".
6. Urutan baris hasil filter tetap urutan server (sisa terbesar dulu).

## Frontend

**`modules/order/lib/receivables-filter.ts` (baru)**

```ts
export type AgeTab = 'all' | 'overdue' | 'soon';

export interface ReceivableFilter {
    q: string;
    line?: BusinessLine;
    age: AgeTab;
}

export function filterReceivables<T extends Pick<ReceivableRow, 'number' | 'customer_name' | 'business_line' | 'days_until_due'>>(
    rows: T[],
    f: ReceivableFilter,
): T[];
```

Pindahkan `ReceivableRow` dari `receivables.tsx` ke `modules/order/types.ts` supaya bisa diimpor lib dan test.

**`modules/order/pages/receivables.tsx`**
- Di atas tabel: `Tabs` (Semua · Lewat jatuh tempo `(n)` · ≤ 7 hari `(n)`) — angka dalam kurung dari seluruh data, bukan hasil filter lain.
- `ListToolbar` mode klien: `value={{ q, line }}`, `filters=[{ key: 'line', label: 'Lini', options: BUSINESS_LINES… }]`, `onChange` langsung `setState` (tanpa debounce yang terasa — komponen tetap debounce 300 ms; untuk daftar puluhan baris itu tidak terlihat).
- `visible = filterReceivables(orders, { q, line, age })`; tabel memakai `visible`.
- Caption aturan 3 muncul hanya bila `visible.length !== orders.length`.
- `KosongTabel` saat hasil filter kosong: `kalimat="Tidak ada piutang yang cocok."` + aksi "Hapus filter"; saat `orders` kosong: tetap `nada="baik"` "Tidak ada tagihan tertunggak." seperti sekarang.
- `payingId` dicari dari `orders` (bukan `visible`) supaya dialog tidak tertutup bila baris hilang dari filter setelah dibayar sebagian.
