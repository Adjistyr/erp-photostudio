# 1.2 Edit order

| Fase | Prioritas | Estimasi | Prasyarat | Keputusan |
|---|---|---|---|---|
| 1 — Data order yang bisa dikoreksi | P1 | L | 0.1 `created_by`, 0.2 `order_events` | K1 (Diserahkan: hanya catatan & customer) |

## Tujuan

Customer menggeser jadwal, ganti jam/lokasi, menambah add-on, atau admin salah pilih customer — kasus mingguan. Hari ini satu-satunya jalan: *Batalkan* (DP tercatat hangus padahal customer tidak batal) lalu *Buat Order* baru dan mencatat ulang DP (yang bisa tertolak `OpenPeriod` bila bulannya sudah tutup). Spek ini menambah edit order dengan batas yang jelas dan setiap perubahan tercatat (0.2).

## Lingkup

**Termasuk**
- Route edit/update, `UpdateOrderRequest` (baru), halaman edit, ekstraksi form bersama `order-form.tsx` (baru).
- Edit field: `customer_id`, `service_date`, `service_time`, `location`, `notes`, dan `items` (tambah/hapus/ubah qty).
- Event `updated` berisi diff.

**Tidak termasuk**
- Edit order **retail** (POS) — koreksi retail = hapus pembayaran / retur (4.2). Item retail sudah diserahkan saat itu juga.
- Mengubah `business_line`, `number`, `discount` (studio/event belum punya diskon), `work_status` (ada route sendiri), `result_link` (route sendiri), pembayaran (route sendiri).
- Item custom (1.3) — ditambahkan ke form yang sama di PR berikutnya.
- Buat customer baru dari form (3.4).

## Aturan bisnis

1. Hanya order lini **studio** dan **event**. Retail → 422 "Order retail tidak bisa diubah — hapus pembayaran atau catat retur."
2. Order **Batal** → 422 "Order yang dibatalkan tidak bisa diubah."
3. Order **Diserahkan** (K1): hanya `notes` dan `customer_id` boleh berbeda dari nilai tersimpan; field lain yang dikirim **harus sama** dengan nilai tersimpan (klien mengirim semua field; server membandingkan). Pelanggaran → 422 pada field terkait "Order sudah diserahkan — jadwal dan item terkunci."
4. Item boleh diubah selama status < Diserahkan **dan** total baru ≥ `totalPaid()`. Pelanggaran → 422 `items` "Total baru Rp X lebih kecil dari yang sudah dibayar Rp Y — hapus pembayaran dulu kalau memang mau mengurangi."
5. Perubahan `service_date` tidak menyentuh uang → **tidak** dicek `OpenPeriod`. Pembayaran tetap di `paid_on`-nya.
6. **Snapshot harga**: item yang dipertahankan (id sama) **tidak** disalin ulang dari katalog — hanya `quantity` yang boleh berubah. Item baru menyalin `name`, `unit_price`, `unit_cost` katalog saat ini. Konsekuensi: dua baris dengan `catalog_item_id` sama bisa punya harga berbeda — itu benar (deal lama vs harga baru), tampilkan apa adanya.
7. Item yang dihapus di form → baris `order_items` dihapus. `order_items` tidak dirujuk tabel lain (`job_costs` merujuk `orders`), aman.
8. `location` kosong untuk studio → default "Studio" (aturan `store()` yang ada, dipakai ulang).
9. `work_status` **tidak** berubah oleh edit, termasuk saat jadwal digeser (Booking tetap Booking, Dijadwalkan tetap Dijadwalkan).
10. Satu event `updated` per simpan, berisi hanya field yang berubah; tanpa perubahan → tidak ada event dan toast "Tidak ada yang berubah."

## Perubahan data

Tidak ada migrasi. `Order` menambah helper yang dipakai request & props:

```php
/** Order yang bisa diedit sama sekali (aturan 1–2). */
public function isEditable(): bool
{
    return $this->business_line !== BusinessLine::Retail && ! $this->isCancelled();
}

/** Jadwal & item terkunci setelah diserahkan (K1). */
public function hasLockedSchedule(): bool
{
    return $this->work_status === WorkStatus::Delivered;
}
```

## Backend

### Route

```php
Route::get('orders/{order}/edit', [OrderController::class, 'edit'])->name('orders.edit');
Route::put('orders/{order}', [OrderController::class, 'update'])->name('orders.update');
```

`orders/{order}/edit` harus didaftarkan **setelah** `orders/create` dan `orders/calendar` (sudah; `{order}` numerik tidak bentrok karena binding gagal → 404 untuk "create", tapi urutan eksplisit lebih aman).

### Request

`Modules/Order/Requests/UpdateOrderRequest.php` (baru), `use ResolvesCatalogLines`:

```php
public function rules(): array
{
    return [
        'customer_id' => ['required', 'integer', 'exists:customers,id'],
        'service_date' => ['required', 'date_format:Y-m-d'],
        'service_time' => ['nullable', 'date_format:H:i'],
        'location' => ['nullable', 'string', 'max:255'],
        'notes' => ['nullable', 'string', 'max:2000'],
        'items' => ['required', 'array', 'min:1', 'max:20'],
        'items.*.id' => ['nullable', 'integer'],          // ada = baris lama; null = baris baru
        'items.*.catalog_item_id' => ['required', 'integer', Rule::exists('catalog_items', 'id')
            ->where('type', CatalogItemType::Service->value)], // TANPA is_active: baris lama boleh merujuk paket nonaktif
        'items.*.quantity' => ['required', 'integer', 'min:1', 'max:999'],
    ];
}
```

Catatan `is_active`: baris **baru** tetap harus aktif — dicek di `after()` (baris tanpa `id` dan katalog `is_active = false` → 422 "Paket sudah nonaktif."). Baris lama boleh merujuk paket yang sudah dinonaktifkan supaya order lama tetap bisa diedit.

`after()` (pola `StoreOrderRequest::after()`, bukan `withValidator`), berurutan, berhenti kalau error sebelumnya ada:
1. `$order = $this->route('order')`; aturan 1–2 → error key `order`.
2. `items.*.id` yang terisi harus milik order ini (`$order->items->pluck('id')`) → 422 `items` "Item bukan milik order ini."
3. Aturan 3 (K1): bila `hasLockedSchedule()`, bandingkan `service_date`, `service_time`, `location` dengan tersimpan dan `items` (id, qty, jumlah baris) → error di field pertama yang berbeda.
4. Aturan 4: `newTotal()` ≥ `$order->totalPaid()`.

Helper di request:
- `newTotal(): int` — Σ baris lama `unit_price_tersimpan × qty_baru` + Σ baris baru `harga_katalog × qty`. **Bukan** `subtotal()` dari trait (trait memakai harga katalog untuk semua baris — salah untuk baris lama). Trait tetap dipakai untuk memuat model katalog (`lines()`).
- `changes(Order $order): array<string, array{from, to}>` — diff field skalar (`customer_id`, `service_date`, `service_time`, `location`, `notes`) + `items` bila ada perubahan (ringkasan `{from: itemsSummary lama, to: itemsSummary baru}`) + `total` bila berubah. Dipakai controller untuk event dan untuk mendeteksi "tidak ada yang berubah".

`attributes()` sama dengan `StoreOrderRequest` + `'items.*.id' => 'item'`.

### Controller / Action / Service

`OrderController@edit(Order $order)`:
- `abort_unless($order->isEditable(), 404)` — bukan 403: order retail/batal memang tidak punya halaman edit, dan tombolnya tidak ditampilkan.
- Props: `customers` dan `catalog` seperti `create()` **ditambah** paket nonaktif yang dirujuk baris lama (supaya Select bisa menampilkan namanya): `CatalogItem::where(is_active)->orWhereIn('id', $order->items->pluck('catalog_item_id'))`, flag `is_active`.
- `order` → `orderProps($order)` + `items[].catalog_item_id`, `items[].unit_cost` (perlu untuk ringkasan margin di form) — tambahkan dua field ini ke `orderProps()` secara permanen (berguna juga untuk 1.3 badge custom).
- `locked: {schedule: bool, items: bool}` = `hasLockedSchedule()` untuk keduanya (hari ini nilainya sama; dua flag supaya 1.3/K1 revisi tidak mengubah bentuk).

`OrderController@update(UpdateOrderRequest $request, Order $order, RecordOrderEvent $events)`:

```
$changes = $request->changes($order);
if ($changes === []) → flash toast "Tidak ada yang berubah." → to_route('orders.index')

DB::transaction:
  $order->update([customer_id, service_date, service_time, location (default Studio), notes (trim ?: null)])
  sinkronisasi item — algoritma:
    $incoming = baris request, dikelompokkan: withId (id terisi) / fresh (id null)
    $keepIds  = withId.pluck(id)
    1. HAPUS: $order->items()->whereNotIn('id', $keepIds)->delete()
    2. UBAH : foreach withId → $item = $order->items->find(id); if ($item->quantity !== qty) $item->update(['quantity' => qty])
              (catalog_item_id, name, unit_price, unit_cost TIDAK disentuh — aturan 6)
    3. TAMBAH: foreach fresh → $catalog = lines()[...]['item']; $order->items()->create([catalog_item_id, name, quantity, unit_price => price, unit_cost => unit_cost])
  $events->execute($order, 'updated', $changes)
flash toast "{number} diperbarui." → to_route('orders.index')
```

Mengganti paket pada baris lama (ubah `catalog_item_id` dengan `id` tetap) **tidak didukung** — klien mengirimnya sebagai hapus + tambah (id null). Server: bila `items.*.id` terisi tapi `catalog_item_id` berbeda dari tersimpan → 422 `items` "Ganti paket dengan menghapus baris lalu menambah yang baru." (menjaga aturan snapshot tetap sederhana).

Field yang masuk `changes` (0.2 `ORDER_FIELD_LABEL` sudah menyediakan labelnya): `customer_id` (from/to = **nama** customer, bukan id, supaya riwayat terbaca), `service_date`, `service_time`, `location`, `notes`, `items` (ringkasan), `total`.
